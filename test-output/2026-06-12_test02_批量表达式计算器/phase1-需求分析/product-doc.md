## B. 场景分析〔承接 U 用户·P 痛点：用用户画像描述「谁在什么场景下遇到了什么痛」〕

**场景 1 — 新表达式开发调试**  
固件工程师正在开发一个将温度传感器原始 ADC 值转为格式化字符串的管道。他打开工具，在表达式框里写 `$1 |> expr($1 / 100.0) |> string.format("%.1f°C", $1)`。填入 ADC 值 `2543`，右侧管道轨迹显示：阶段 1 入 `2543` → 出 `25.43`；阶段 2 入 `25.43` → 出 `"25.4°C"`。确认正确，复制表达式进代码。**原始 Demo 已解决这个场景，但空状态无引导，新用户第一次打开不知该填什么。**

**场景 2 — 批量回归验证**  
QA 工程师改了字符串替换表达式，想验证不破坏现有 80 条测试用例。切换到用例模式，粘贴 CSV 数据（每行：输入 + 期望输出）。加载后执行全部，两秒内看到结果。**原始 Demo 能完成这个场景，但统计列标签（Total/Success/Failed）是英文，与中文界面割裂；执行后无法筛选「只看不匹配项」，需要肉眼逐行找差异。**

**场景 3 — 含模板变量的表达式调试**  
工程师的表达式含 `${threshold}` 动态参数，在宿主 VS Code 扩展里会由外部配置注入。在不启动宿主的情况下他想单独调试这段逻辑。**原始 Demo 不支持模板变量，他只能临时把 `${threshold}` 改成硬编码值，改完再改回来，每次 3-5 分钟。**

**场景 4 — 历史表达式恢复**  
工程师下午改版一个上午写过的格式化表达式。打开工具，原始 Demo 没有历史记录。他只能翻代码注释或重新从头写，约 5 分钟。**原始 Demo 不支持历史持久化，这个场景完全摩擦。**

## D. 核心流程〔承接 P 痛点 → 操作顺序约束与高频操作步骤直接从 P 维痛点提炼〕

**调试模式（高频，每次开发都用）：**

```
1. 编写/修改表达式  [必须第一步]
2. 应用表达式（Ctrl+Enter 或点按钮）  [触发解析，参数框按解析结果渲染，必须在 3 之前]
3. 填写 $1/$2... 参数值  [实时触发求值]
4. 查看管道轨迹（阶段中间值）  [自动]
5. 复制结果 / 调整表达式  [任意顺序重复]
```

**用例模式（中频，回归验证时用）：**

```
1. [沿用调试模式的已应用表达式，或先完成调试模式步骤 1-2]
2. 切换到用例模式
3. 粘贴 CSV 测试数据  [必须在 4 之前]
4. 加载用例  [验证格式，必须在 5 之前]
5. 执行全部（F5 或点按钮）
6. 查看结果 / 筛选 / 导出
```

**关键依赖约束（不可违背）：**
- 参数输入框在「应用表达式」后才生成，步骤 2 不完成则无法到步骤 3
- 执行按钮在「加载用例」成功后才出现，步骤 4 不完成则无法到步骤 5

## G. 注意事项洞察〔汇合 B·P 的约束面：B 维预算/技术约束 + P 维「踩坑风险」→ 设计红线〕

| # | 约束/风险 | 设计红线 |
|---|---------|---------|
| G1 | 单文件约束：CSS/JS 必须内联，无外部 CDN | 所有优化方案必须保持零外链；不能引入任何 `<script src="...">` |
| G2 | `normOut` 模糊比较：字符串 `"7.00"` 与数字 `7.00` 视为匹配 | 需在结果页面添加「比较规则」说明，避免用户误以为严格类型匹配 |
| G3 | `$N` 参数上限歧义：参数 ≥10 时 `$10` 与 `$1` 正则冲突 | UI 层可显示警告；工程上应修复（按索引降序替换） |
| G4 | `string.gsub` `%d+` 量词 bug | 文档/工具提示中说明当前 Lua 量词支持限制，直到修复 |
| G5 | localStorage 多窗口共享 | 不同 VS Code 窗口间历史/设置可能互相覆盖；应在同一 origin 下加前缀区分 |
| G6 | `executeBatch` 同步阻塞主线程 | 1000+ 用例时 UI 卡顿；大批次应分块执行或用 Web Worker |
| G7 | postMessage 协议未统一 | 宿主侧键名需与工具侧保持一致，否则注入失效 |
