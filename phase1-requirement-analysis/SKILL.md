# 阶段一 · 需求输入 → 分析报告 · 可视化报告 · Demo 提示词

本 skill 是「需求 → 工程」两阶段流水线的**第一阶段**，提炼并重构自 openUBMC Studio
三个前置实践（代码→产品文档、后端代码→设计反向分析、高保真→Demo→工程代码）。

核心理念：
> **任何需求形态都先被翻译成结构化分析，再渲染成两类产物——给人看的可视化报告、给 AI 看的 Demo 提示词。**
> 分析这一步最容易被省略，但它是后续所有设计与工程决策的地基。
> 代码里、文字里、草图里都藏着产品的真实逻辑，读懂它，才能做有根据的判断，而不是靠猜。

整条流水线：

```
【阶段一 · 本 skill】
需求输入（代码/文字/草图/一句话/简易文档）
  → 1.1 内容阅读与分析（功能定义·场景·用户画像·核心流程·机会点·竞品·注意事项）
  → 1.2 生成预览页面 + 第一轮 /design-critique 设计审查
  → 1.3 [输入为代码时] 后端代码阅读：数据结构·接口契约·业务逻辑梳理
  → 产出：可视化报告 + Demo 提示词文档 (+ 代码梳理三件套)

         ⬇ 用户把 Demo 提示词输入到「生成 Demo / 精调已有 Demo」环节

【阶段二 · phase2-demo-to-data skill】
精调后的 Demo 产物
  → /design-critique + /accessibility-review
  → design-structure.md / tech-selection.md / 工程代码 / 接入说明 / README / CHANGELOG
```

## 需求分析

### 用户与痛点

| 角色 | 典型场景 | 核心痛点 |
|------|---------|---------|
| 体验设计师 | 后端代码或一句话需求先于设计稿到达，需要快速理解「这个东西是做什么的」 | 看到一堆字段名和整数编码，不知道哪些和用户有关、哪些是内部机制；想做设计审查但没有业务上下文，结论流于表面 |
| 产品经理 | 接手无文档的存量工具，或只有一句话的新点子，要向团队解释清楚 | 只能靠运行软件或脑补来猜功能，边界不清，容易遗漏约束条件 |
| 前端开发 | 接手陌生代码仓或模糊需求，要先建立业务理解再开发 | 字段命名用工程术语（`cmd_word: 0x30440100`），不知道含义；改一处不知道会不会影响别处 |
| 后端工程师 | 查看设计侧对自己交付物的反馈 | 希望问题描述精准，能明确哪些需要后端配合改 |
| 新加入的团队成员 | 没有老员工传背景，自学理解系统 | 文档散落在代码注释和口口相传里，找不到全貌 |
| 项目负责人 | 评估某个需求值不值得做、怎么做 | 缺少结构化的场景/机会点/竞品判断，决策没有抓手 |

**设计师的深层痛点**：
工程工具类产品（固件配置、硬件调试、工业控制）的输入里充满了设计师不熟悉的技术概念——十六进制命令字、位字段、通信拓扑、表达式语法。这些不是障碍，是信息富矿。关键在于建立一套从「技术表达」翻译到「设计判断」的方法。

### 场景

1. **后端先行、无文档交付**：工程师完成了实现但没有产品说明。以代码为一手资料，反向建立对产品的理解，再做设计介入。
2. **一句话/草图起步**：只有一个模糊点子或手绘草图，需要先把它撑成完整的功能定义、场景、用户画像，才能开始做 Demo。
3. **新增视图的场景分析**：产品迭代时新增了若干界面，逐一分析：面向谁、什么情境下打开、解决什么问题、有哪些机会点。
4. **设计审查的上下文准备**：在做设计审查之前，先建立产品上下文，让审查结论有业务依据而非泛泛而谈。
5. **技术编码的设计语言翻译**：把工程师的表达（`pid_control_mode: 1`、`cmd_word: 0x30440100`）翻译成用户能理解的语言，建立设计-开发共同词汇表。
6. **存量系统设计改进**：改进现有工具体验，需要先读懂数据结构和业务逻辑，才能判断哪些改动安全、哪些有风险。

### 设计点

- **翻译是设计工作**：把 `pid_control_mode: 1/2/3/4` 翻译成「慢升快降（省电优先）」，这个过程本身就是设计判断——选择什么语言、粒度多细、用什么隐喻。
- **分析决定下游质量**：带着「核心用户是在嘈杂机房里长时间使用的固件工程师」这个上下文去做 Demo 提示词和设计审查，精准度会高出 10 倍。
- **机会点分级决定优先级**：分清「前端独立实现」「需后端配合」「需产品层决策」，让改进建议可落地而不是空谈。
- **提示词是给 AI 的设计简报**：Demo 提示词不是把需求复述一遍，而是把分析结论压缩成「视觉规格 + 数据结构 + 交互规则 + 业务约束」的可执行简报。
- **两类产物，两类读者**：可视化报告给人（评审、对齐、汇报），Demo 提示词给 AI（生成/精调原型），同一份分析渲染成两种形态。
- **功能规格可移植，设计系统可插拔**：提示词里「做什么」（能力、状态、数据结构、交互）与「长什么样」（颜色、字体、间距、组件）要解耦。前者跨项目复用；后者是一个**可替换的设计系统单元**，换项目只换它。目标是「优化一次提示词，之后每次生成的 Demo 都自动对齐当前项目的设计系统」，而不是每个项目重写视觉。

## 输入

本阶段接收**任意形态**的需求输入，先识别类型再分流处理：

| 输入类型 | 示例 | 处理重点 |
|---------|------|---------|
| 后端代码 / 配置 | GitHub/GitCode 链接、本地目录、YAML/JSON/源码 | 走全量分析 + 1.3 代码梳理三件套 |
| 数据模型文档 | `data-model.md`、OpenAPI spec、ERD | 信息密度最高，优先阅读 |
| 样本数据 | `sample-*.yaml`、`*.json` 样本文件 | 快速理解字段实际值域 |
| 辅助工具代码 | VSCode 插件、CLI 工具、解析脚本 | 业务规则的隐性载体 |
| 一段文字 / 简易文档 | 需求描述、PRD 片段、会议纪要 | 提取功能、场景、用户、流程；缺失处主动追问 |
| 一张草图 / 截图 | 手绘线框、白板照片、参考界面截图 | 识别布局意图、组件、交互热点 |
| 一句话 | 「做个风扇调速配置工具」 | 用追问把它撑成完整需求，再分析 |

> **输入越稀疏，追问越重要。** 一句话/草图类输入，先用 AskUserQuestion 或直接提问补齐：目标用户是谁、核心任务是什么、有没有已知约束。不要在关键信息缺失时凭空捏造。

## 工作流

### Step 0 — 识别输入类型并分流

先判断输入属于上表哪一类，决定走哪条路径：

- **代码/配置类** → 完整跑 Step 1（含 1.5 模块识别、Step 2 数据模型、Step 2+ 技术概念）+ **Step 1.3 代码梳理三件套** + Step 1.1 分析 + Step 1.2 预览审查。
- **文字/文档类** → 跳过代码专属步骤，从文字中提取功能/场景/用户/流程，缺失处追问，再做 Step 1.1 + 1.2。
- **草图/截图类** → 先用 Step 1.1 的视觉读图（识别布局、组件、热点），再补功能与场景分析，再做 1.2。
- **一句话类** → 先追问补齐，撑成可分析的需求，再按文字类处理。

> 代码输入时，**1.3 的代码阅读在 1.1 之前先做**——读懂数据结构和业务逻辑，才能写出有根据的功能定义和机会点。本文档按用户的 1.1/1.2/1.3 编号组织，但执行顺序按依赖关系来。

---

### Step 1.1 — 内容阅读与分析

无论输入是什么，都要产出以下七项分析，写入 `product-doc.md`，并作为可视化报告和 Demo 提示词的素材来源。

#### A. 功能定义

一句话说清「这是什么、给谁、解决什么」，再展开核心功能清单。
代码输入时，从入口文件 + 数据模型 + 关键流程反推；文字/草图输入时，从描述与视觉意图提取。

#### B. 场景分析

2–4 个具体场景，用叙事描述：用户在做什么 → 遇到什么 → 怎么用 → 得到什么。
> 场景描述用完整叙事：「工程师正在排查……他打开……他看到……他点击……结果……」

#### C. 用户画像分析

| 维度 | 内容 |
|------|------|
| 角色 | 职业 + 技术背景 |
| 使用频率 | 高频/低频/一次性 |
| 使用环境 | 嘈杂机房 / 安静办公室 / 移动端 / 大屏 |
| 核心诉求 | 用户真正想达成的目标 |
| 典型触发点 | 什么事件让用户打开这个功能 |

#### D. 核心流程

还原用户完成一个完整任务的操作顺序，标注：
- 必须按顺序完成的步骤（先定义实体，再建立引用）
- 可任意顺序完成的步骤
- 步骤间的依赖约束

#### E. 设计机会点分析

每个机会点标注实现层级：🟢 前端可独立实现 / 🟡 需后端配合 / 🔴 需产品层决策。

> **机会点必须分两类穷尽，不能只列「修问题」级——这是分析最容易偷工的地方。**
>
> - **(a) 问题修复型**：消除已暴露的缺陷（审查发现的、痛点对应的）。容易想到。
> - **(b) 专业级完成度型**：高频专业用户期待、但当前**完全缺失**的能力。最容易被漏，却是「能用」与「专业工具」的分水岭。
>
> 挖 (b) 类的自检三问（每个工具都要过一遍）：
> 1. **用户一天用 50 次，哪些动作还在重复手工？** → 往往指向「历史 / 复用 / 收藏 / 最近项」「示例 / 模板 / 重置」。
> 2. **产出要去到哪些下游？** → 往往指向「多格式导出（原始值 / C 字面量 / JSON / 命令行）」「一键复制 / 回写宿主」。
> 3. **这个数据结构最该被「看见」的是什么？** → 往往指向「全保真可视化」（如 32-bit 命令字应逐位画出，而非只给一个比例条）「双向同步」「联动高亮」。
>
> **真实教训（SMC 计算器）**：首轮分析只挖到「语义常驻 / 复制 / 三态 / 比例位条」等问题修复型，漏掉了「逐位 32-bit 位图、HEX↔DEC 双向同步、多格式导出 C/JSON、最近 10 次历史、示例/重置」这一整类专业能力，导致优化后 Demo「正确但单薄」。分析阶段就把 (b) 类当**必查项**，下游 Demo 才会有专业完成度。

随后将所有机会点汇总为一张**三列流视图**，表达「痛点 → 洞察 → 策略」的因果链，而不是平铺列表：

| 列 | 内容 | 写法要求 |
|----|------|---------|
| 第一列 | **用户痛点** | 具体、可量化，带操作成本 |
| 第二列 | **洞察汇聚** | 从多个痛点提炼的深层原因，通常比痛点少（多对一） |
| 第三列 | **设计策略** | 对应洞察的具体设计方向，标注 🟢/🟡/🔴 |

**洞察汇聚的写法**：不是痛点的复述，而是提炼「为什么这些痛点会同时出现」的深层原因。

```
错误写法：「命令字操作难」（只是痛点 P1 的重复）
正确写法：「翻译比填写更高频」（解释了 P1+P2 为什么同时出现的根因）
```

在可视化报告的 synthesis slide 里，这张三列流视图以 SVG 连线图渲染（见 Step 1.2 报告规格），不是表格。

#### F. 对标竞品分析 + 专利潜力

竞品分析的重点是找「差距」，而不是罗列功能：

```
| 竞品 / 行业方案 | 具备的能力 | 与本功能的差距 |
|----------------|-----------|--------------|
```

> 差距是设计决策的依据——「我们能做而别人没做」才是机会，「别人做了一样的」只是参考。

专利潜力评估回答三个问题：
1. 这个功能组合（操作方式 × 界面交互模式 × 应用场景）在行业内是否有先例？
2. 差异化点是哪几个关键词的**组合**（注意是组合，而非单个关键词）？
3. 评级：**高**（组合未见先例）/ **中**（组合新颖但单项不稀缺）/ **低**（已有公开先例）

**专利描述原则**：专利点只从**用户交互操作角度**描述——触发方式、界面交互模式、状态连续性设计等，不引用前端实现技术（WebView、localStorage、API 名称等）。

```
✗ 错误描述：「使用 localStorage 缓存表达式历史」
✓ 正确描述：「用户完成计算后，历史记录自动出现在下次打开时，无需手动保存」
```

#### G. 注意事项洞察

约束条件、边界情况、被移除或未实现功能对设计的技术约束、魔法值陷阱、动态字段陷阱等。

#### 逐模块分析框架（输入含多个功能模块时）

代码/复杂文档输入时，先做**功能模块识别与边界确认**：

扫描结构，按功能边界聚类，识别独立功能模块。判断依据：
- 有独立的子目录或文件前缀命名
- 有自己的 WebView / Provider / 数据类型定义
- 使用场景完全不同，即便入口相邻或共享部分代码

区分「独立功能模块」与「同一模块的子功能」——子功能共享数据模型或操作上下文，归并到父模块分析，不单独展开。

**输出模块清单，在继续之前发给用户确认**：

```
| 模块 | 一句话描述 | 是否独立分析 |
|------|-----------|------------|
| XXX  | ...       | ✅ 是      |
| YYY  | ...       | ❓ 待确认  |
```

遇到以下情况，**等用户确认再继续**：
- 两个功能共享部分代码但使用场景明显不同（入口相邻不等于同一功能）
- 某个模块规模很小，不确定是否值得独立展开
- 某个功能被版本历史或注释标注为「已移除」「实验性」或「WIP」

确认后，只对用户明确要分析的模块进入后续步骤。对每个模块，按以下 7 项固定结构展开（即 A–G 的逐模块版本）：

| 项次 | 内容 | 说明 |
|------|------|------|
| 1 | **需求背景** | 这个功能从哪来？为什么存在？在整体技术栈/产品体系中的位置 |
| 2 | **概念解释 + 图示** | 核心技术概念用最简语言解释，搭配结构图（不懂业务的人也能看懂） |
| 3 | **使用场景** | 2–4 个叙事场景 |
| 4 | **目标用户** | 角色、频率、环境、核心诉求、典型触发点 |
| 5 | **痛点分析** | 当前没有工具时的操作成本（量化）；每条痛点段落结尾固定「**痛点核心：**……」 |

### Step 1.1+ — 陌生技术概念的识别与解释

读代码或读专业需求时，你会遇到各种「看不懂」的东西——一个奇怪格式的数字、一段自定义语法、一个专业术语缩写。这不是障碍，是信息密度最高的地方。**这些解释要写进 product-doc.md 的概念章节，并在可视化报告的 concept slide 呈现。**

**判断一个技术概念是否需要解释的标准**：
> 如果一个刚入职的体验设计师/开发新员工看到这个词/值/格式，会不会有疑问？
> 会 → 需要解释。 不会 → 直接使用，不用额外说明。

#### 如何解释任何陌生技术概念：四步法

**① 它是什么？**（用一句话，不用行话）把概念还原成最朴素的描述，用「这是一种……用来……的东西」句式。
**② 为什么要这样设计？**（工程师的动机）找到他们这样做的原因——通常是节省空间、提高效率、或遵循硬件规范。理解动机才能理解边界。
**③ 它具体怎么工作？**（用实例 + 图示）用一个具体真实例子走一遍，必要时画结构图。「走一遍」比「讲原理」有效得多。
**④ 对用户/设计意味着什么？**（翻译回界面语言）这个概念在界面上应该怎么呈现？用户在哪一步接触它？对交互有什么约束或机会？

#### 什么时候用图示，什么时候用文字

| 情况 | 推荐方式 |
|------|---------|
| 概念有明确结构（位分段、层级关系、网络拓扑） | 画结构图（ASCII 图或表格）|
| 概念涉及时序或流程（操作步骤、状态变化） | 画流程图或时序图 |
| 概念是一个类比（「就像……一样」） | 文字类比 + 一个对比例子 |
| 概念是枚举值（选项 A/B/C 各是什么意思） | 映射表格 |
| 概念是纯数值关系（公式、换算） | 带注释的计算示例 |

**原则：** 如果你读了自己写的解释还是觉得模糊，就加一个图。图的目的不是美观，是消除歧义。

#### 三类高频出现的技术概念（附解释示范）

**类型一：编码整数（一个数字里藏了多段信息）**

工程代码里常出现一个看起来像乱码的数字，比如 `0x30440100`。它实际上是把多段信息「压缩」进了一个整数。

*① 它是什么？* 一种把多个字段打包进同一个数字的存储方式。就像一个压缩文件——外面看是一个文件，解压后里面有很多东西。
*② 为什么这样设计？* 硬件通信时每次只能发送固定长度的数据（比如 4 个字节 = 32 位）。工程师把多个字段塞进这 32 位，既满足协议要求，又一次性传递所有必要信息。
*③ 它具体怎么工作？*（需要画图解释）

```
十六进制和二进制的对应关系：
每 1 位十六进制字符 = 4 位二进制（称为一个"nibble"）
8 位十六进制 × 4 = 32 位二进制

0x  3    0    4    4    0    1    0    0
   ↓    ↓    ↓    ↓    ↓    ↓    ↓    ↓
  0011 0000 0100 0100 0000 0001 0000 0000
  └─────────┘ └─────────┘ └─────────┘ ...
   第一个字段    第二个字段   第三个字段
```

工程师把字段边界设计在 nibble 边界上，这样用肉眼看十六进制字符就能分辨各字段——这是选择十六进制表示的根本原因。

字母的含义（十六进制用 0–9 和 A–F 表示 0–15）：
```
A=10  B=11  C=12  D=13  E=14  F=15
0xC = 12（十进制）= 1100（二进制）
```

同一个数里有时混用十六进制和十进制：有些字段代表「编码/地址」（用十六进制，因为位结构有意义），有些代表「数量/序号」（用十进制，因为数字本身有意义）。

用户如何获得这些字段定义？**不是从数字本身推导**，而是从外部规格文档（芯片手册、寄存器表、协议文档）查到的——文档里会写「第 24–31 位是功能码，第 16–23 位是命令码」，用户按定义来填写或解读。

*④ 对设计意味着什么？*
- 用户不应手动填写这个整数，UI 应把各字段拆成独立输入框
- 用户填好各字段后，UI 在后台合并生成完整编码值
- 需要显示「当前命令字预览」，让用户确认生成的值符合预期
- 字段之间可能有约束（某字段值会影响另一字段的可选范围），需要联动校验

**类型二：领域表达式语言（产品自定义的迷你语法）**

代码里出现一种「不像普通代码也不像自然语言」的语法，比如 `ReadRegister(channel=2, offset=0x0C, length=4)` 或 `<=/Scanner_Lm75_Inlet.Value`。

*① 它是什么？* 一种专门为这个产品设计的指令语法，介于「人话」和「编程语言」之间。用于描述计算逻辑、查询条件或操作规则。
*② 为什么这样设计？* 让不会写代码的用户（运维人员、工程师）也能描述「我想做什么操作」，不需要学一门完整的编程语言。
*③ 它具体怎么工作？*（关键是区分不同的使用模式）

```
调试模式（即席执行）          用例模式（脚本化复用）
─────────────────────         ──────────────────────
用户意图：「我现在想试         用户意图：「我要定义一套
试这条指令是否有效」           可反复执行的标准操作」

→ 填一条表达式                → 填多条表达式，组成序列
→ 立刻执行，看结果             → 保存为「用例」，按需触发
→ 不保存                      → 可共享给团队

类比：计算器 vs 宏录制
```

输入参数的作用：
```
不带参数：ReadRegister(channel=2, offset=0x0C)  ← 只能读这一个寄存器
带参数：  ReadRegister(channel=$ch, offset=$off) ← 模板，可复用

批量执行：ch = [0, 1, 2, 3]，offset = 0x0C
→ 自动执行 4 次，分别读取 channel 0/1/2/3 的同一个寄存器
→ 相当于「一个表达式，多组输入，对比结果」
```

*④ 对设计意味着什么？*
- 调试模式和用例模式是两种不同的使用意图，不能共用同一个表单加一个开关了事
- 切换模式时，用户已填写的内容不能丢失
- 参数输入需要类型提示和值域说明（`$ch` 应是整数，取值 0–7）
- 批量执行的多组结果适合表格对比展示，不适合逐条显示

**类型三：通信拓扑（命令发给谁）**

代码里有各种设备地址（`0x48`、`0x2C`）和总线编号（`i2c_bus: 1`），还有「发送命令」「广播」之类操作。这描述的是一个硬件通信网络。

*① 它是什么？* 多个硬件设备连接在一条共享线路上，每个设备有唯一「门牌号」（地址）。发送命令时指定门牌号，命令才能准确送达目标设备。
*② 为什么这样设计？* 硬件资源有限，不能为每对设备拉专用线。共享总线 + 地址寻址是经济实用的多设备通信方案。I2C、SPI、CAN 等都是这类协议。
*③ 它具体怎么工作？*

```
通信主机（发令者）
     │
     ├── 总线 0 ────┬── 地址 0x48：进风口温度传感器
     │              └── 地址 0x4A：排风口温度传感器
     │
     └── 总线 1 ────┬── 地址 0x2C：风扇控制器
                    └── 地址 0x58：电源管理芯片

发送命令 → 指定「总线 + 地址」→ 只有那个设备响应
广播命令 → 不指定地址（地址 0x00）→ 总线上所有设备都响应
```

命令字和拓扑的关系：命令字里通常有一个字段是「目标设备地址」，指向拓扑图里的某个节点。命令字决定「做什么」，拓扑决定「发给谁」。

*④ 对设计意味着什么？*
- 用户选择「发给谁」时，应能看到设备列表或拓扑图，而不是手动填写地址数字
- 发送前应显示「将发送给：[设备名称]（地址 0x48，总线 0）」，让用户确认目标
- 广播操作影响所有设备，必须有二次确认警告
- 拓扑结构变化（新增设备）时 UI 应能反映，不依赖用户手动更新地址

#### 遇到其他陌生技术概念时的处理原则

1. **先问「这解决了什么问题」**——工程师不会无缘无故发明复杂概念，找到动机是理解的捷径。
2. **找最小可理解的例子**——不要试图先理解全貌，找一个最简单的真实值（如 `0x30440100`），走一遍完整解析过程。
3. **用类比建立直觉**——「就像……」的类比往往比技术定义有效 10 倍。好类比的标准：听的人说「哦，就是那个意思啊」。
4. **画出来**——任何有结构的概念（层级、分段、网络），画出来后通常立刻清晰。不需要漂亮，ASCII 图已经够用。
5. **最后问「所以呢」**——翻译回界面语言：这个概念对用户操作有什么影响？界面上应该怎么处理？

| 维度 | 逐项检查（打勾即过，发现即记为 Finding） |
|------|----------------------------------------|
| **信息架构** | 内容分组是否符合用户心智？最重要的信息是否在第一屏/视觉重心？导航深度（工程工具 ≤3 层）？关联实体能否在同一视图内访问？ |
| **视觉层级** | 第一眼落点是不是核心任务？同等重要的元素是否等权重、主次是否拉开？信息密度是否与用户专业度匹配（非越密越好）？ |
| **视觉一致性** | 同类操作是否同一种控件/位置？装饰符号（emoji/图标/分隔）是否统一？主次按钮权重是否明确？ |
| **反馈与状态** | 空/加载/错误/成功/禁用是否都有设计（不能只有 happy path）？合法零值是否与"空/错"区分？魔法值是否转人类可读？枚举整数是否有标签？技术字段名是否有说明？ |

> 每条 Finding 必须**可量化**：「内容孤岛感严重」是主观，「宽屏下内容集中在左 750px，右 1/3 纯空白」才是可验收。每条都要能直接转成 demo-prompt.md §C 的一行目标状态。

```
请基于以下产品背景进行审查：
- 产品类型：[工程工具 / 消费者应用 / 管理后台]
- 核心用户：[职业 + 技术背景 + 使用频率 + 使用环境]
- 核心任务流：[从 product-doc.md 摘取]
- 已知约束：[技术栈限制、不可改动的后端约定]
- 特殊数据格式：[如有位字段命令字、表达式语言，说明用户如何与之交互]

```

审查覆盖：信息架构、视觉一致性、反馈与状态、层级清晰度。
**审查结论必须并入可视化报告**（critique slide），并标注每条：🔴 Critical / 🟡 Moderate / 🟢 Minor。

> 产品文档是审查工具的放大镜——同样的「对比度不足」，有了「核心用户是在嘈杂机房里长时间使用的固件工程师」这个上下文，严重程度和修复优先级会完全不同。

### Step 3 — 生成 Demo 提示词文档（demo-prompt.md）

> 这是本阶段给「下游 Demo 生成/精调」的核心交付物。它不是需求复述，而是把分析压缩成一份**可执行的设计简报**。

#### 先判断模式：从零生成 vs 存量优化

两种场景对提示词的要求截然不同，**必须先判断再写**：

| 模式 | 触发条件 | 提示词的核心价值 |
|------|---------|----------------|
| **绿地模式**（从零生成） | 无现有 UI，从功能描述/代码/草图出发 | 把功能逻辑 + 用户场景 + 数据结构压缩成 AI 能落地的设计起点 |
| **优化模式**（存量改进） | 有现有 UI（截图/代码），目标是改进设计 | 从现有代码提取设计系统基线 + 精确量化当前问题 + 给出每个问题的可验收目标状态 |

> **为什么优化模式需要单独处理？**
> 用「功能正确的绿地提示词」去做设计优化，AI 会从头重构而不是改进——忽略已有色彩体系、发明新组件、不解决具体的视觉问题。优化模式的提示词核心是「锚点」：给 AI 一个不能偏离的设计系统基线，再在这个基线上指定改进方向。

#### 优化模式必查：专业级完成度补齐清单

> **优化 ≠ 只修审查发现的问题点。** 用「只修问题」的提示词，AI 会做出一个「干净但单薄」的版本——审查问题没了，但仍不是一个专业工具。优化模式的提示词必须显式要求补齐下面这些高频专业能力（逐项判断「本工具要不要」，要则写成 §C/§E 的可验收规格，不要则注明「本轮不做」并说明原因）：

| 能力类别 | 典型形态 | 适用判断 |
|---------|---------|---------|
| **全保真可视化核心数据** | 编码整数 → 逐位/逐段位图；拓扑 → 图；曲线 → 可编辑曲线 | 数据结构本身有「结构」就要可视化，且要全保真（逐位而非比例条） |
| **历史 / 复用 / 最近项** | 最近 N 次、收藏、模板、localStorage 持久化、点击回填 | 用户会重复产生同类结果时必加 |
| **多格式导出** | 原始值 / HEX / DEC / C 字面量 / JSON / 命令行片段 + 实时预览 | 产出要进代码/配置/工单等多个下游时必加 |
| **双向 / 多入口同步** | HEX↔DEC、字段↔整体、图↔表，单一数据源驱动全联动 | 同一数据有多种表示时必加 |
| **快速起点** | 载入示例、模板、重置、清空 | 几乎所有工具都该有 |
| **逐元素操作** | 每字段/每行单独复制、读数、语义标签、行内校验 | 复合数据（多字段/多行）必加 |
| **键盘加速** | 快捷键（Ctrl+S 收藏、Enter 提交、Esc 关闭） | 高频专业用户必加 |

> 在 demo-prompt 里把选中的能力写成带数值/格式的可验收规格（如「最近 10 次，localStorage key `xxx.v2`，点击回填全部字段」「JSON 导出形如 `{...}`」），而不是「加个历史功能」这种模糊描述。

#### 提示词写作要点（两种模式通用）

- **绿地模式**：把第一轮审查的 🔴/🟡 问题转成正向约束；魔法值/枚举映射必须显式列出；空/错误/加载状态不能空着。
- **优化模式**：§A（设计系统基线）决定 AI 不发明新配色；§B（量化诊断）决定 AI 知道改什么；§C（目标状态映射）决定 AI 知道改成什么样；缺少任何一个，改进就会漂移回「重新设计一遍」而非「有针对性的改进」。
- **两种模式共同的陷阱**：只写功能需求，不写视觉/交互规格 → AI 会做出功能正确但设计平庸的结果；只写问题，不写目标状态 → AI 会发散而非聚焦。

### Step 3.5 — 用提示词产出优化后 Demo（阶段间过渡产物，必出）

> demo-prompt.md 的终点不是文档本身，而是**一个能看、能点的优化后 Demo**。不要把提示词丢给用户就结束——直接用它产出 Demo，让"优化后是什么样"看得见，这也是阶段二的输入。

- **⚠️ 前置确认（生成前唯一必问项）：插入哪个设计系统？** 视觉决策不由本 skill 拍板，而是**委托给一个可替换的「设计系统单元」**。每个项目视觉标准不同，所以设计系统是插拔的——同一份功能规格，插不同设计系统就渲染成不同视觉。生成前用 AskUserQuestion 确认：**当前项目用哪个设计系统？**（已 vendored 的设计系统包 / 某 GitHub 设计系统 / 沿用输入自带样式 / 无，用通用基线）。
  > **关键分离：功能规格（可移植）× 设计系统（可插拔）= 每次都对齐。** 能力规格（位图/历史/多格式导出/双向同步…，见 §B/§C）描述「做什么」，与视觉无关，跨项目复用；设计系统决定「长什么样」，是换项目时唯一要替换的槽位。
  > 真实教训：盲跑原始 SMC HTML，能力广度一次到位，唯一缺口就是「该用哪个设计系统」——这是输入里没有线索、只能从外部插入的信息。把它做成槽位，而不是每次硬编码或重猜。
- **委托给插入的设计系统（若有包）**：很多设计系统本身就是一个 skill / 文件包（带 token、class、pattern、自己的 Workflow），如 `pto-design-system`。生成 Demo 时**把视觉决策整段委托给它**：
  > 先读 `<design-system>/SKILL.md` 与 `DESIGN.md`/`tokens`/`references`；把本 Demo 的每个元素映射到它的 token/class/pattern（产出一张迁移对照表：元素 → 它的 class/token → 要删的旧装饰）；**只用它的视觉语言，不自创颜色/按钮/卡片/间距**；按它的 Workflow（如 PTO 的 Workflow B 改造、Workflow A 新建、Workflow C pattern-first）执行；命中 IDE/图/泳道/架构等场景时先走它的 pattern。
  - 此时 demo-prompt 的 §A 不再写死 hex，而是写「设计系统 = `<name>`，视觉一律遵循其规则」。能力规格（§B/§C）保持视觉无关。
- **直接生成（无外部设计系统时）**：依据 demo-prompt.md 产出 `optimized-demo/index.html`——**单文件、可双击、零依赖**。视觉用「沿用输入自带样式」或通用基线，并在顶部标注「设计系统槽位：未指定」。这是"便宜的实验"，刻意用单文件形态，区别于阶段二"昂贵的承诺"。
- **⚠️ 交付前必须真渲染验证，并把设计系统 CSS 内联进单文件。** 两条死规则，违反任意一条都算没交付：
  1. **内联，不外链**：当委托外部设计系统时，最终交付的 Demo 必须把该系统的 CSS（token + class 实现）**内联进单文件**，而不是 `<link href="../../ds/style.css">`。外链相对路径一旦文件被单独打开/移动，CSS 直接 404——而 token 化 CSS 没有 fallback，整页会塌成无样式的裸 HTML。要么内联，要么明确用本地 server 起、且把设计系统一起带上。
  2. **真打开看过再说"完成"**：用浏览器（headless 截图即可）实际渲染一次，确认不是裸 HTML、配色/布局/组件到位、控制台无报错；并核对**核心逻辑结果正确**（如编解码往返、关键计算用真实值跑一遍），不是只看它能显示。**「文件存在 / CSS 里没硬编码色 / 类型通过」都不等于「渲染对、算得对」**——token 没加载时这些静态项全过、页面却全黑/全白崩掉。没渲染、没跑过就别声称达标。
- **优化模式要锚定基线**：从原 Demo 提取的设计系统（§A）一分不差地沿用，只在其上落实 §C 的目标状态——不发明新配色、不从头重画。
- **必须覆盖**：demo-prompt 里列出的 🟢 改进项、空/零/错三态、魔法值与枚举映射、可访问性基线（语义常驻、≥12px、focus 可见、错误多通道）。
- **保真度**：视觉规格能精确就精确（hex+px）；数据用 Mock，不写死实例进结构；字段命名对齐后端约定（Mock 即契约）。
- **不做**：工程级拆分、API 层、测试、框架化——那是阶段二。Demo 只验证设计方向。

> 产出后，优化后 Demo 与 demo-prompt.md 一起交接给阶段二；阶段二的设计审查/可访问性审查/uxspec 都以**这个优化后 Demo**为对象，而非原始 Demo。

### Step 4 — 生成可视化分析报告（16:9 幻灯片格式）

将研究结论 + 第一轮设计审查输出为一份 **16:9 幻灯片格式（slide deck）的 HTML 可视化报告**，供设计评审、团队对齐、向上汇报。

**报告形态硬约束（本节最重要的部分）：**
- 整份报告是一个**幻灯片 deck**，一次只显示一张 slide（方向键 / 点击画布两侧 / 顶部按钮翻页），**不是长页滚动**。
- **每张 slide 的比例恒定 16:9**，做法是「固定画布 1280×720 + 整体 transform scale 自适应」：窗口怎么变，slide 永远 16:9 不变形，只是整体等比放大缩小并居中。
- 单文件、零依赖，不输出裸 HTML、不自创零散样式。

> ⚠️ 为什么用「固定画布 + 整体缩放」而不是 `vw`/`%` 逐元素自适应？因为整张 1280×720 画布统一 `scale()`，内部所有 px（字号、间距、卡片）会一起等比缩放，比例绝对不变；用 `vw` 逐个元素自适应会在不同窗口比例下走形、错位。**内部一律用固定 px，不要用 vw/vh/%。**

#### 核心技术：16:9 固定画布 + 宽度自适应缩放（必须照此实现，勿改缩放逻辑）

```css
*,*::before,*::after{box-sizing:border-box;margin:0;padding:0}
html,body{width:100%;height:100%;overflow:hidden;background:#e0e0e5;
  font-family:-apple-system,BlinkMacSystemFont,'Segoe UI','PingFang SC','Noto Sans CJK SC',sans-serif}
/* 居中容器：占满视口 */
.deck-wrapper{width:100vw;height:100vh;display:flex;align-items:center;justify-content:center;overflow:hidden}
/* 固定画布：1280×720 = 精确 16:9，整体由 JS scale() 等比缩放 */
.deck{position:absolute;width:1280px;height:720px;transform-origin:top left;background:#f5f5f7;
  overflow:hidden;box-shadow:0 24px 80px rgba(0,0,0,.18)}
/* 顶部固定导航条 40px */
.deck-header{position:absolute;top:0;left:0;right:0;height:40px;z-index:200;display:flex;
  align-items:center;gap:10px;padding:0 20px;background:rgba(255,255,255,.94);border-bottom:1px solid #d2d2d7}
/* 单张 slide：一次只显示一张，占满画布除去 header 高度；超出一律 hidden 不滚动 */
.slide{display:none;position:absolute;top:40px;left:0;right:0;bottom:0;
  padding:26px 48px 28px;overflow:hidden;flex-direction:column;color:#1d1d1f}
.slide.active{display:flex}
```

```js
// ① 16:9 等比缩放：窗口变化时整体缩放并居中，比例永远不变
function resizeDeck(){
  const deck = document.getElementById('deck');
  const ww = window.innerWidth, wh = window.innerHeight;
  const scale = Math.min(ww / 1280, wh / 720);   // 取小值：完整可见、不裁切
  deck.style.transform = `scale(${scale})`;
  deck.style.left = ((ww - 1280 * scale) / 2) + 'px';
  deck.style.top  = ((wh -  720 * scale) / 2) + 'px';
}
window.addEventListener('resize', resizeDeck);
resizeDeck();

// ② 翻页：一次一张
const slides = document.querySelectorAll('.slide');
let current = 0;
function goTo(n){
  slides[current].classList.remove('active');
  current = Math.max(0, Math.min(slides.length - 1, n));
  slides[current].classList.add('active');
  document.getElementById('counter').textContent = `${current+1} / ${slides.length}`;
  if(slides[current].id === 'synthesis') setTimeout(drawConnections, 80); // 三列流连线重绘
}
const go = d => goTo(current + d);
document.addEventListener('keydown', e=>{
  if(e.key==='ArrowRight'||e.key==='ArrowDown') go(1);
  if(e.key==='ArrowLeft' ||e.key==='ArrowUp')   go(-1);
});
// 点击画布左 1/4 上一页、右 1/4 下一页（避开顶部导航）
document.getElementById('deck').addEventListener('click', e=>{
  if(e.target.closest('.deck-header')) return;
  const x=e.clientX, w=window.innerWidth;
  if(x < w*.25) go(-1); else if(x > w*.75) go(1);
});
```

#### 产出契约（强制）

1. **单文件 HTML**：整份报告就是一个 `[product-name]-report.html`，CSS 全部内联在 `<style>`、JS 内联在 `<script>`，双击即开、零依赖。幻灯片场景**不拆 shared.css**，从根上杜绝「样式没加载成纯文本」。
2. **必须包含**上面的 `.deck-wrapper > .deck`（1280×720）结构 + `resizeDeck()` 缩放逻辑 + 翻页逻辑，三者缺一不可。
3. **内部全部固定 px**，不用 `vw`/`vh`/`%` 控制字号与关键尺寸。
4. **一次只显示一张 slide**（`.slide{display:none}` / `.slide.active{display:flex}`），不是长页滚动。
5. **顶部导航条品牌名（`.hdr-brand`）只写用户明确告知的产品名称**：
   - 用户说了产品名 → 填入该名称，原文照写，不改不加工
   - 用户没有提供产品名 → `.hdr-brand` 留空（`<div class="hdr-brand"></div>`）或整体省略，**绝不自己起名字、推断名字、或从需求内容中猜测名字**
6. 生成后过「交付前自检」再交付。

**关键坐标换算**：deck 用 `transform: scale()` 缩放，`getBoundingClientRect()` 返回的是**屏幕像素**，必须除以当前 scale 才能换算回 1280×720 画布坐标系，连线才不会错位：

```js
function drawConnections(){
  const deck=document.getElementById('deck'), svg=document.getElementById('opp-svg');
  if(!svg) return;
  const m = deck.style.transform.match(/scale\(([^)]+)\)/);
  const scale = m ? parseFloat(m[1]) : 1;
  const svgBox = svg.getBoundingClientRect();
  const pt = el => { const r=el.getBoundingClientRect();
    return { x:(r.left - svgBox.left)/scale, y:(r.top - svgBox.top)/scale, w:r.width/scale, h:r.height/scale }; };
  // 用 pt(节点) 取坐标，连 M x1,y1 C … 的贝塞尔曲线，stroke-dasharray 画虚线
}
```

连线含义：多个痛点汇聚到一条洞察，每条洞察导出一个设计策略。

#### 交付前自检（不通过不交付）

1. **单文件可双击打开**，CSS/JS 全内联，无任何外部依赖（不依赖 shared.css）。
2. **比例不变形**：随意改变浏览器窗口大小 / 进入全屏，slide 始终 **16:9**，整体等比缩放并居中，四周露出 `#e0e0e5` 底色边，**不出现滚动条、不裁切内容**。
3. **翻页可用**：方向键 ←/→（或 ↑/↓）能翻页，计数器显示「n / 总数」，点击画布左右两侧也能翻页。
4. **单页不溢出**：每张 slide 内容在 1280×720 内装得下，无内部滚动、无被 `overflow:hidden` 切掉的内容；溢出就拆成多张。
5. **是幻灯片不是长页**：一次只显示一张，不是纵向滚动的长文档。
6. **用组件而非裸标签**：`card`/`chip`/`table`/`flow-card` 等，而非纯文本堆叠。
7. 本地预览 `python3 -m http.server 8765` 或直接双击，确认呈现「居中的 16:9 卡片式幻灯片」，而非截图里那种黑字蓝链接纯文本长页。

## 来自 openUBMC Studio 的实践笔记

**先读数据模型，再读代码。** `data-model.md` 里的信息密度比源代码高得多——它已经做了一次结构化，从这里开始能省大量时间。

**样本数据是最好的字段说明书。** `sample-cooling.yaml` 里的真实值告诉你字段的实际值域，比类型定义（`string`）更有用。

**魔法值是最优先要找的。** `32768`、`-1`、`"N/A"` 这类特殊值往往藏在业务逻辑里，不找就会漏到 UI 上——这是最容易被用户骂的那类 bug。

**十六进制不是障碍，是结构信号。** 看到 `0x30440100` 不要跳过——它告诉你这个值被分成了 4 段，每段 8 位、各有含义。设计师的工作是把这些段翻译成用户能填写和理解的字段。

**位字段的来源永远是外部文档，不是命令码本身。** 用户不是「拿到命令码来解析字段」，而是「先有规格文档知道各段含义，再按规格填写命令码」。UI 的目标是让规格文档里的字段定义变成用户的操作界面。

**合法零值不是空值。** 数值/编码类工具里，`0x00000000`、`0`、全默认字段往往是一个**合法**结果，不是「未输入」。如果空态、零态、错误态共用同一个结果区且同色（如都显示红），用户会把合法零值误判成错误。分析时把「空 / 零 / 错」当三个独立状态，提醒下游 Demo 三态分色——这是数值工具最常见的状态设计陷阱。

**调试模式和用例模式的根本差异是使用意图，不是功能差异。** 调试是「我要试试这条命令」，用例是「我要定义一套可重复操作」。两者的 UI 结构应反映意图差异，而非共用一个表单加 toggle。

**通信拓扑的可见性直接影响操作安全性。** 工程师发一条命令影响的是一个具体物理设备，UI 里看不出命令发给了谁就容易误操作。让「命令目标」在每次操作前可见，是工程工具最基本的安全设计。

**输入越稀疏，分析越要主动追问。** 一句话/草图类需求，凭空捏造比承认「这里待确认」危害大得多。把假设显式标成待确认清单，是对下游 Demo 和工程负责。

**Demo 提示词是给 AI 的设计简报，不是需求复述。** 把分析压缩成「视觉规格 + 数据结构 + 交互规则 + 业务约束 + 已知审查问题」，AI 才能生成高质量 Demo，而不是又猜一遍。

**Mock 数据 = API 契约，从提示词阶段就对齐。** demo-prompt.md 里的字段命名要和后端约定一致（`lastLoginAt` 而非 `last_login`），这样阶段二的工程 API 层是替换而非重写。

**产品文档是审查工具的放大镜。** 同样的「对比度不足」，有了核心用户上下文，严重程度和修复优先级会完全不同。
