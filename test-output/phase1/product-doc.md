# SMC 偏移量计算器 · 产品文档

## 技术栈概览

原生 HTML + CSS + JavaScript 单文件，无框架、无构建、零依赖。运行在 VS Code Webview 中（用 `--vscode-*` 主题变量），文件头做了 standalone polyfill 以便独立双击预览。所有逻辑是 32 位命令字的位字段编解码，纯本地计算，无网络请求。

## SMC 偏移量计算器

### 需求背景

BMC（基板管理控制器）固件里，对部件的每一次操作都被编码成一个 32 位「SMC 命令字（offset）」。工程师在写配置、查日志、调寄存器时，手上经常是一个十进制大整数（如 `809893888`）或一段十六进制，需要在「整数」和「功能码/命令码/读写方向…」之间来回换算。手算要做移位和掩码，易错且慢。这个计算器把双向换算工具化。

### 功能定义

一句话：**给 BMC 固件工程师用的、SMC 32 位命令字 ↔ 5 个语义字段的双向编解码器，解决「手算位运算易错」的问题。**

核心功能：
1. **正向编码**：填功能码/命令码/MS/RW/参数 → 实时算出 32 位命令字（hex + dec）。
2. **反向解码**：粘一个十进制/十六进制偏移量 → 一键拆解回 5 个字段。
3. **实时校验**：每个字段按位宽/范围即时过滤与校验；溢出 32 位时取低位并告警。
4. **应用/取消**：把算好的命令字应用（回写）或复位重来。

### 使用场景

1. **照规格填命令字**：工程师拿到协议文档「散热部件、命令 0x0102、读操作」，打开计算器：功能码填 `06`、命令码 `0102`、RW `1`，实时结果区立刻显示 `0x18040500`（示意），复制进配置。省去手算移位。
2. **反查一条日志里的偏移量**：排障时日志打印 `offset=809893888`，看不出是哪个部件的什么操作。把它粘进十进制框点「解析」，字段区拆出 `function=0x0C / command=0x1180 / …`，立即定位。
3. **批量核对**：评审一批寄存器配置，逐个粘进去解码，核对功能码是否落在预期部件域，揪出填错部件的条目。

### 目标用户

| 维度 | 内容 |
|------|------|
| 角色 | BMC/固件工程师、硬件调试、测试工程师；具备十六进制与位运算基础 |
| 使用频率 | 中频、阵发——写/审一批配置时高频连用，平时不开 |
| 使用环境 | VS Code 内（常是较窄的侧边/底部面板），暗色主题；实验室或办公室 |
| 核心诉求 | 快速、零错地在「整数」与「语义字段」之间互转，并能把结果拿走 |
| 典型触发点 | 照协议文档写命令字；或在日志/寄存器里遇到一个看不懂的 offset 大整数 |

### 用户痛点

- **P1 手算位运算易错**：6/16/1/1/8 的字段边界**不在半字节上**（功能码 6 位、命令码 16 位跨 nibble），肉眼看十六进制无法直接分段，手动移位掩码每次要几十秒且常错一位。**痛点核心：字段边界不对齐 nibble，使「看一眼就懂」不可能，必须借工具。**
- **P2 语义藏在 tooltip 里**：MS=1 是「单读」、RW=1 是「读」、功能码 `0x06`=「散热部件」——这些映射只在 hover tooltip 出现，填的人得记忆或反复悬停。**痛点核心：核心语义不可见，工具只帮算数不帮理解。**
- **P3 结果拿不走**：算出 `0x30460000` 后没有复制按钮，得手动选中长串十六进制，易漏字符。**痛点核心：主产出（命令字）缺少一键带走的出口。**
- **P4 空态/零态/错误态同形**：默认 `0x00000000` 与清空字段后的 `0x--------` 都出现在同一结果区，零值（合法）与未填（无效）视觉区分弱。**痛点核心：合法零值与缺失/错误状态混淆。**

### 核心操作流程

```
路径A 正向编码（无强制顺序）
  任意顺序填 5 字段 → (300ms 防抖) 实时结果区出 hex+dec → 点「应用」回写 / 复制
路径B 反向解码
  十进制框粘 offset（支持 0x）→ 点「解析」→ 5 字段回填 → 实时结果区同步
两条路径汇聚到同一组字段状态；可随时互转。
约束：应用需「全字段合法」；解析需「输入非空可解析」。
```

#### 特殊技术概念说明：编码整数（位字段命令字）

用四步法（见 phase1 概念框架）：
- **是什么**：把 5 段信息打包进一个 32 位整数的存储方式，像压缩包——外面是一个数，解开有 5 个字段。
- **为什么**：硬件通信一次发固定 4 字节(32 位)，工程师把多个字段塞进这 32 位，既满足协议又一次传齐。
- **怎么工作**：

```
位:  31              26 25                      10  9  8 7            0
    ┌─────────────────┬─────────────────────────┬──┬──┬─────────────┐
    │  功能码 6-bit    │      命令码 16-bit        │MS│RW│  参数 8-bit  │
    └─────────────────┴─────────────────────────┴──┴──┴─────────────┘
注意：功能码(6)与命令码(16)都不落在 4 的倍数边界上，
      所以无法靠"数十六进制字符"分段——必须做位移/掩码。
encodeOffset = (fn<<26)|(cmd<<10)|(ms<<9)|(rw<<8)|param
```

- **对设计意味着**：用户不该手填整数，UI 把它拆成 5 个独立输入框，后台合并并实时预览；字段语义（枚举）应当**常驻可见**，而非藏在 tooltip；非半字节对齐这一点，是放一张「位布局可视化」最有价值的地方。

### 设计机会点

> ⚠️ **机会点要分两类穷尽，不能只列「修审查问题」级**：
> （a）**问题修复型**（消除已暴露缺陷）；（b）**专业级完成度型**（高频专业用户期待、当前完全缺失的能力——这类最容易被分析漏掉，却是「能用」与「专业工具」的分水岭）。
> 自检三问帮挖（b）类：① 工程师一天用 50 次，哪些动作还在重复手工？（→ 历史/复用）② 算出的结果要去到哪些下游？（→ 多格式导出 C/JSON）③ 这个数据结构最该被「看见」的是什么？（→ 全保真 32-bit 位图）。

**(a) 问题修复型**

| # | 机会点 | 痛点 | 建议方向 | 实现层级 |
|---|--------|------|---------|---------|
| O1 | 功能码语义常驻 + hint 浮层 | P2 | 字段值常驻语义标签；hover/focus 弹样式化速查表（非原生 title） | 🟢 前端 |
| O2 | MS/RW 语义化 | P2 | 带标签控件 + hint，底层存 0/1 | 🟢 前端 |
| O3 | 结果复制 + 动效 | P3 | 复制按钮 + copied 态 + toast | 🟢 前端 |
| O4 | **完整 32-bit 位图** | P1 | 逐位 32 格显示 0/1、字段 hue 着色、字段带 + 位号标尺 + 边界线（**按真实位区间，非半字节等分**） | 🟢 前端 |
| O5 | 空/零/错三态区分 | P4 | 占位灰 / 强调蓝 / 错误红，三态分明 | 🟢 前端 |

**(b) 专业级完成度型（之前分析遗漏，本轮补强）**

| # | 机会点 | 缺口 | 建议方向 | 实现层级 |
|---|--------|------|---------|---------|
| O8 | **HEX↔DEC 双向同步输入** | 只能单向 | 顶部两个输入框实时双向联动，字段/位图同步刷新 + synced 指示 | 🟢 前端 |
| O9 | **多格式导出** | 只能拿走原始 hex | 拆分按钮菜单：HEX / DEC / HEX+DEC / **C 字面量** / **JSON 字段**，各带实时预览 | 🟢 前端 |
| O10 | **「最近 10 次计算」历史** | 算过的拿不回 | localStorage 持久化 + 点击回填 + Ctrl+S 收藏 + 时间戳 + 清空 | 🟢 前端 |
| O11 | **字段权重按位宽布局** | 等宽 grid | 字段卡用 `6fr 16fr` / `1fr 1fr 2fr` 成比例，命令码最显眼 | 🟢 前端 |
| O12 | **载入示例 / 重置** | 无快速起点 | 一键填整齐示例命令字 / 一键清空回占位态 | 🟢 前端 |
| O13 | 每字段 dec/hex 读数 + 单独复制 | 字段值不透明 | 卡片 foot 常驻 DEC/HEX + 单字段复制按钮 | 🟢 前端 |

**(c) 需规格/产品决策**

| # | 机会点 | 建议方向 | 实现层级 |
|---|--------|---------|---------|
| O6 | 功能码语义校验 | 区分已定义/保留(0x20)/OEM(0x37-3F)/未定义空洞，分别提示 | 🟡 需规格 |
| O7 | 功能码×命令码联动 | 若规格有合法命令表，按功能码联动命令码可选范围 | 🔴 需决策 |

> **分析教训**：本工具第一轮分析只挖到 O1–O7（多为问题修复），漏掉了 O8–O13 这一整类专业级能力。原因是分析停在「审查发现了什么」，没有主动问「专业用户一天用 50 次还缺什么」。优化模式的需求分析必须把（b）类机会点当作**必查项**，否则产出的 Demo 会「正确但单薄」。

### 竞品分析

| 竞品 / 行业方案 | 具备的能力 | 与本功能的差距 |
|----------------|-----------|--------------|
| 通用程序员计算器（Windows Calc 程序员模式、各类在线 bit 计算器） | 进制转换、按位查看/翻转 | 不懂 SMC 语义——不知道哪段是功能码、`0x06`=散热；纯位操作无业务标签 |
| 寄存器位字段查看器（如 SVD viewer、Cmsis-SVD 工具） | 按设备描述文件拆位字段、带名字 | 需要 SVD/描述文件；面向寄存器调试而非 SMC 命令字编辑；不内置这套部件域枚举 |
| 手写 Python/脚本 | 完全可定制 | 无 UI、不可分享、每次重写、易错；非工程师不可用 |

> 差距即机会：**「SMC 命令字专用 + 双向 + 语义常驻 + 一键带走」这个组合**，通用计算器和寄存器工具都没整合。

### 专利潜力评估

- 差异化关键词组合：**位字段命令字** × **双向实时编解码** × **语义枚举常驻可见（非 tooltip）** × **非半字节对齐字段的位布局可视化联动**。
- 行业先例：单项均有（位计算器、寄存器查看器），但「面向特定 SMC 协议、双向、语义常驻 + 位布局联动高亮」的**组合**未见明确公开先例。
- 评级：**中**——组合新颖，但每个单项都不稀缺；若叠加 O7（功能码↔命令码规格联动校验）可上探到「中高」。
- 描述原则（仅交互角度）：✓「用户填写语义字段后，命令字与其位布局实时高亮联动呈现，反向粘贴整数可一键拆回各语义字段」；✗ 不写 `encodeOffset`/DOM/具体实现。

### 设计注意事项

1. **零值不是空值**：`0x00000000` 是合法命令字，别用「错误红」表达它。
2. **字段边界不对齐 nibble**：任何「按十六进制字符切分」的可视化都是错的，必须按真实位区间(31-26/25-10/9/8/7-0)着色。
3. **语义来源是外部规格**：功能码枚举来自协议文档，不是从数值推导；UI 应把规格变成可选项，并为「保留/OEM/未定义」留出表达。
4. **窄面板优先**：宿主常是 VS Code 窄面板，布局要在窄宽都成立，不能假设宽屏两栏。
5. **主产出要可带走**：命令字 hex 是工程师真正要的东西，复制路径必须一步到位。

## 第一轮设计审查结论（/design-critique，本轮以现有 Demo 为对象）

> ⚠️ 环境未安装 `/design-critique` skill，本轮审查按其四维度框架人工执行（这是一条对 skill 的发现，见调整记录）。完整结论已并入可视化报告 `critique` slide。

**Usability**
- 🔴 核心语义（功能码枚举、MS/RW 含义）只存在于 `title` hover tooltip：键盘/触摸不可达，且大段多行文本塞进 tooltip 难读——工具「帮算不帮懂」。
- 🟡 结果区无复制按钮，主产出（hex 命令字）需手动选中长串，易错（P3）。
- 🟡 「应用」会顺带把结果写进十进制输入框，副作用不直观。

**Visual Hierarchy**
- 🟡 命令码（16-bit，信息量最大）与 MS/RW（1-bit）在网格里仅靠 `.wide` 跨列区分，位宽差异(16 vs 1)未在视觉权重上充分体现。
- 🟡 缺少「位布局」这一最能体现命令字结构的视觉锚点。

**Consistency**
- 🟢 标题用 🧮、结果区用 ⚡、section 用 `◆` 伪元素，三套装饰符号混用，与 VS Code 简洁风格略有出入。

**Accessibility**
- 🟡 错误/警告文案 11px、`field-bits` 10px、help-icon 11px——偏小，长时间使用吃力。
- 🟡 字段非法仅靠红色文字（`.invalid` 改 color）+ 文案，无图标，色觉障碍不友好；空字段与错误字段同视觉（P4）。
- 🟡 `❓` tooltip 仅 hover 可见，无 `aria`，屏幕阅读器/键盘用户拿不到这套关键语义。
